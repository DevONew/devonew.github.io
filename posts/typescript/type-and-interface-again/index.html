type과 interface 다시 생각하기

📅2026년 5월 20일
TypeScriptFrontend타입React

type과 interface에 대해 알려주세요.

또는 "type과 interface는 어떻게 쓰시나요"는 면접에 가면 생각보다 자주 듣는 질문이다. 어느정도 답변은 할 수 있지만 늘 그렇게 만족스러운 대답을 한건 아닌 느낌이 자주 든다. 우선 면접관들의 표정이 미묘(..)했다는 점과 이런 질문을 괜히 하지 않기 때문이다. 그래서 이번 기회에 다시 한번 진득하게 공부를 했는데 생각보다 충격적이었다. 나는 type과 interface는 취향차이라고 생각했는데 설계철학에 따라 철저하게 다르게 생긴 것이었다. 그러니까 사실 저런 질문들의 의도는 " 이 둘의 차이(문법 차이)를 알고 있는가"가 아니라 "이 두 개가 왜 다른 목적으로 만들어졌는지 이해하고 있는가" 였다.

둘 다 코드에서 변수나 함수의 타입을 미리 선언해두는 문법이지만 어떤게 다른지 또 어떤 목적으로 설계된건지 한번 살펴보자.

type - 타입 별칭 선언(Type Alias Declaration)

type은 기존 타입 표현식에 식별자를 바인딩 하는것이다. 즉 이미 존재하는 타입(또는 타입 조합)에 별칭(alias)를 붙이는것이다. 우변엔 원시 타입, 객체, 유니온(|), 인터섹션(&), 함수 시그니처, 조건부 타입, 매핑 타입까지 전부 허용된다.

type Age = number;

type ID = string | number;

type Handler = (e: Event) => void;

type Partial<T> = { [K in keyof T]?: T[K] };

type User = {
  id: string;
  name: string;
};

핵심은 별칭이다. type Age = number라고 해도 Age가 새로운 타입을 만든게 아니라 number를 가리키는 또 다른 이름일 뿐이다. 컴파일러 입장에서는 Age는 number의 구조적으로 동일한 참조일 뿐이라 타입 체크 시 완전 치환이 가능하다.

interface - 객체 타입 선언(Object Type DEclaration)

interface는 JS에 원래 없던 개념이다. TS가 객체지향언어의 인터페이스 개념을 가져오게 되면서 만든 문법이다. 그래서 오직 객체의 형태만 기술할 수 있다.( 다른 말로는 구조 계약을 명시한다고 한다.)

interface User {
  id: string;
  name: string;
}

겉보기엔 type으로 쓴 객체와 똑같아보이지만 interface는 "이 객체는 이런 속성을 가진다"는 계약(구조)을 선언하는 문법이라 유니온이나 원시타입 별칭 같은 건 불가하다.

결정적인 차이

다 아는 내용이고 너무나 명확한 차이지만 그럼에도 정리해본다.

1. type의 표현 범위가 훨씬 넓다.

위에서 언급 했듯이 interface는 객체 모양만 기술 가능하지만 type은 여러 고급 타입 조작이 가능하다.

2. 확장 메커니즘이 다르다.

interface는 객체지향언어의 인터페이스를 가져왔기 때문에 extends로 상속 체인을 형성한다.

interface Extended extends Base {
  name: string;
}

type은 인터섹션(&)으로 구조적 병합을 한다.

type Base = { id: string };
type Extended = Base & { name: string };

3. 타입체커의 에러 리포팅 방식이 다르다.

충돌 처리 방식이 다른데 interface 같은 경우, 타입충돌을 즉시 에러로 알려주고 type은 never로 계산해버려 에러없이 그냥 못쓰는 타입이 된다. 이게 대규모 코드베이스에서는 은근히 디버깅 비용을 늘리는 지점이 된다고 한다. 따라서 TS공식 문서에서는 명시적으로 에러 메세지가 필요할때는 interface를 권장한다.

interface Person {
  name: string;
}
interface Person {
  name: number;
} // 에러 뜸: 같은 속성, 다른 타입이라 충돌

type Person1 = { name: string };
type Person2 = { name: number };
type Staff = Person1 & Person2;
declare const staffer: Staff;
staffer.name; // 타입이 never로 조용히 계산됨

4. 선언 병합은 interface만 가능하다.

interface는 TS 컴파일러가 두 선언을 하나의 타입으로 자동 병합해준다.

interface Window {
  customProp: string;
}
interface Window {
  anotherProp: number;
}

type의 경우 동일 스코프에서 재선언 시 Duplicate identifier 에러가 나는데 그렇기 때문에 외부 라이브러리의 타입정의 확장을 할 때는 interface가 필수다.

언제 무엇을 써야할까?

실무에서 흔한 컨벤션 중 하나는, 컴포넌트 props처럼 유니온이나 Pick/Omit 조합이 자꾸 섞이는 곳은 type, API 응답 모델 처럼 객체 정의하는 곳엔 interface로 권장한다.

잠깐 성능 차이가 있나?

이걸 쓰다 보니 갑자기 생각이 났는데 성능 차이가 있을까? 그래서 약간의 서치를 해본 결과, 대규모의 코드베이스에서는 성능차이가 실제로 있다는것을 발견했다!

TypeScript 공식 퍼포먼스 위키와 Sentry의 실제 사례에 따르면 type의 인터섹션(&)을 남발하면 코드베이스가 커질수록 타입 체크 속도가 느려진다고 한다. Sentry는 실제로 React 앱 곳곳에서 HTML 타입을 인터섹션으로 확장하던 패턴 때문에 IDE와 tsc 속도가 심하게 느려졌던 적이 있고, 이를 interface extends로 바꿔서 개선했다. interface는 내부적으로 병합된 하나의 flat 구조로 캐싱되는 반면 type의 인터섹션(&)은 매번 재계산이 들어가기 때문이다.

그리고 성능과는 좀 다른 얘기긴 한데 interface가 훨씬 익숙한 문법이기 때문에 편하다고 한다. 실제로 이 생각을 리액트 진영에서도 채택해 "기본은 interface, type은 필요해지면 바꾼다"는 전략을 쓴다.

결론

팀 프로젝트 세팅글에 잠깐 짧게 썼었는데 어딘가에 기록하지 않으면 그대로 까먹을거 같아서 블로그에 정리해봤다. 생각보다 합리적인 배경들이라 이해하는데 더 쉬웠던거 같다. 차이를 무작정 달달 외웠을땐 자주 헷갈렸는데 이렇게 배경부터 보니 더 이상 헷갈릴 일은 없을듯 싶다.
