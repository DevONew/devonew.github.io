Vite manualChunks로 재배포 시 재다운로드 용량 줄이기

📅2026년 8월 10일
Vite프론트엔드

개요

작년 회사에서 AI 사주팔자 서비스를 개발할 때 했던 Vite 청크 분리 작업을 정리해보려 한다. 시간이 꽤 지났지만 지금 돌아봐도 꽤 유용한 지식이라, 잊어버리기 전에 블로그에 남겨두고자 한다.

이 프로젝트는 웹페이지(앱 없이 웹만)였고, 빌드 도구로 Vite를 썼다. 개인적으로는 그동안 Vue만 다뤄왔고 React는 이 프로젝트가 처음이었던 터라, 뭔가 이상한 걸 느껴도 "React라서 원래 이런가?" 싶어 한동안 넘겼던 기억이 있다.

문제 발견

코드를 수정하고 나서 빌드를 하거나, 배포된 페이지에 들어갔을 때 묘하게 느려지는 느낌을 받았다. 처음엔 리액트가 처음이라 내가 뭔가 잘못 짜서 그런가 싶었는데, 곱씹어보니 코드를 수정할 때마다 이 느려지는 정도가 조금씩 더 심해지는 것 같았다. 그래서 "빌드/배포 자체의 구조 문제 아닐까?"라는 의심으로 방향을 바꿔 네트워크 탭을 열어봤다.

거기서 이상한 점을 발견했다. 앱 코드 한 줄만 고쳐서 재배포했을 뿐인데, 사용자가 브라우저에서 다시 받는 JS 용량이 수정 전이랑 거의 같았던 것이다. React 같은 라이브러리는 그대로인데도 왜 매번 전체를 새로 받아야 하는 걸까 싶었다.

라이브러리 의존성이 꽤 큰 프로젝트라, 배포 한 번에 사용자가 다시 받아야 하는 용량도 무시할 수 없는 수준이었다.

원인 분석

먼저 Vite가 뭔지 짚고 넘어가면, Vite는 개발 서버 구동과 프로덕션 빌드를 담당하는 프론트엔드 빌드 도구다. 개발 중에는 ESM을 활용해 필요한 모듈만 즉시 컴파일해서 서버를 빠르게 띄워주고, 프로덕션 빌드 시에는 내부적으로 Rollup을 사용해 코드를 번들링한다. Webpack 기반 빌드 대비 개발 서버 구동/HMR 속도가 빠르다는 게 흔히 알려진 장점인데, 지금 다룰 문제는 이 "빌드" 단계, 정확히는 Rollup이 번들을 묶는 방식에서 비롯된다.

Vite(Rollup) 기본 빌드는 앱 코드와 node_modules의 라이브러리 코드를 구분하지 않고 하나의 번들로 묶는다. 결과물은 index-[hash].js 하나로 나오고, 이 해시는 번들 전체 내용을 기준으로 생성된다.

문제는 여기서 시작된다. 앱 코드를 한 글자만 고쳐도 번들 전체의 해시가 바뀌기 때문에, 브라우저 입장에서는 파일명이 통째로 바뀐 완전히 새로운 파일로 인식한다. 라이브러리 코드는 한 바이트도 바뀌지 않았는데도 캐시를 재사용할 방법이 없는 것이다. 결국 배포할 때마다 사용자는 변경되지 않은 vendor 코드까지 매번 새로 다운로드하고 있었다.

해결: manualChunks로 vendor/앱 코드 분리

원인이 "번들이 하나로 묶여서 해시도 하나"라는 데 있으니, 해결 방향은 명확했다. 라이브러리 코드와 앱 코드를 별도 청크로 분리해서 각자 독립적인 해시를 갖게 만드는 것이다.

Vite 설정에서 build.rollupOptions.output.manualChunks를 사용해 node_modules에서 온 모듈을 모두 vendor 청크로 묶었다.

// vite.config.ts
export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        manualChunks(id) {
          if (id.includes("node_modules")) {
            return "vendor";
          }
        },
      },
    },
  },
});

이렇게 하면 빌드 결과물이 vendor-[hash].js와 index-[hash].js(앱 코드)로 나뉜다. 앱 코드를 수정해도 index-[hash].js의 해시만 바뀔 뿐, vendor-[hash].js는 내용이 그대로라 해시도 그대로 유지된다. 브라우저는 이 파일을 캐시에서 그대로 재사용한다.

결과

앱 코드를 한 줄 수정하고 재배포한 뒤 사용자가 실제로 다시 받는 JS 용량을 비교했다.

  • 적용 전: 199KB (라이브러리 코드까지 통째로 재다운로드)
  • 적용 후: 11KB (변경된 앱 코드만 재다운로드)

약 94% 절감이다. 배포 빈도가 잦은 프로젝트일수록 이 차이는 누적된다. 코드 한 줄을 고칠 때마다 사용자가 불필요하게 반복 다운로드하던 용량이 사라진 셈이다.
