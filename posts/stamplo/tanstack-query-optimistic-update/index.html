팀 코드로 이해하는 낙관적 업데이트

📅2026년 7월 20일
StamploTeam ProjectTanStack QueryReact낙관적 업데이트

개요

어드민 페이지의 미션 관리 기능엔 드래그로 순서를 바꾸는 D&D 기능이 있는데, 여기에 수정 시 블러 처리되어 느려 보이는 이슈가 있었다. 팀원이 현업에서는 이런 걸 어떻게 처리하는지 멘토님께 여쭤봤고, 낙관적 업데이트로 해결했다. 팀플은 끝났지만 이 낙관적 업데이트가 정확히 뭔지 궁금해져서 공부하는 겸 정리해보았다.

낙관적 업데이트

보통의 순서는 서버의 요청이 끝나야 화면이 바뀐다. 그러나 낙관적 업데이트는 순서가 조금 다른데 어차피 요청은 성공할 것이라 가정하고 서버의 응답을 기다리지 않은 채 화면을 먼저 바꿔버린다. 그래서 성공 시 그대로 두고 실패하면 원래 상태로 되돌린다. 이것이 낙관적 업데이트의 개념이라고 할 수 있다. 좋아요,D&D 순서 바꾸기 등 "실패할 가능성은 낮지만 반응 속도가 중요한" 동작에 주로 사용하는 편이다.

Tanstack와 낙관적 업데이트

사실 낙관적 업데이트는 Tanstack Query의 발명품이 아니다.

사실 위에서 말했듯이 낙관적 업데이트는 프론트엔드 개발 전반의 일반적인 UX 패턴/개념 이다. 따라서 React든 Vue든, 심지어 순수 JS로 구현할 수가 있다.

간단하게 JS로 구현해본 낙관적 업데이트

button.onclick = async () => {
  heartIcon.classList.add("filled"); // 먼저 화면 바꿈
  try {
    await fetch("/api/like", { method: "POST" });
  } catch {
    heartIcon.classList.remove("filled"); // 실패하면 되돌림
  }
};

순수 리액트로 구현해본 낙관적 업데이트

function LikeButton({ initialLiked }: { initialLiked: boolean }) {
  const [liked, setLiked] = useState(initialLiked);

  const handleClick = async () => {
    const previous = liked;
    setLiked(!previous); // 먼저 화면 바꿈

    try {
      await fetch("/api/like", { method: "POST" });
    } catch {
      setLiked(previous); // 실패하면 되돌림
    }
  };

  return <button onClick={handleClick}>{liked ? "❤️" : "🤍"}</button>;
}

TanStack Query는 여기서 뭘 해주나

위 LikeButton처럼 useState만으로도 낙관적 업데이트는 가능하지만, 실제 앱에선 단순 값이 아니라 서버 목록/상세 데이터 자체를 낙관적으로 바꿨다가 롤백해야 한다. TanStack Query가 없던 시절엔 이런 서버 데이터를 다룰 때 보통 이렇게 했다.

  • 서버 데이터를 useState로 들고 있는다
  • useEffect로 fetch해서 그 state를 채운다
  • 로딩 상태, 에러 상태도 각자 useState로 따로 관리한다
  • 같은 데이터를 여러 컴포넌트가 쓰면, 각자 따로 fetch하거나 props로 내려주거나 Context로 감싸야 한다

이렇게 된다면 1. 서버에 있는 데이터의 현재 상태를 여기저기서 각자 따로 들고 있게 되고 2. 그렇기에 일일이 각 컴포넌트 별로 직접 위 내용을 구현해야된다.

TanStack Query는 서버 데이터를 캐시라는 하나의 중앙 저장소로 관리해준다. 같은 쿼리키를 쓰는 컴포넌트는 모두 이 캐시를 공유하기 때문에, 컴포넌트 개별이 아니라 캐시 차원에서 데이터를 관리할 수 있다. 즉 어딘가에서 데이터를 바꾸면 그 캐시를 구독하는 다른 컴포넌트들도 알아서 같이 업데이트된다.(queryClient.setQueryData(...))
또한 onMutate/onError/onSettled라는 표준화된 자리를 제공해서, 낙관적 업데이트를 훨씬 깔끔하고 일관되게 구현할 수 있게 해준다. (내가 직접 일일이 로직을 짜지 않아도 된다.)

TanStack Query에서의 구현 방식

useMutation 이라는 훅에 세 개의 콜백을 등록해서 이 흐름을 구현한다.

콜백실행 시점하는 일
onMutate요청을 보내기 직전화면(또는 캐시)을 미리 바꾼다. 나중에 실패했을 때 되돌리기 위해,
바꾸기 전 원래 값을 저장해뒀다가 반환한다.
onError요청이 실패했을 때onMutate가 저장해둔 원래 값으로 되돌린다.
onSettled성공하든 실패하든 마지막에 항상서버의 진짜 최신 데이터를 다시 가져와서 화면과 맞춘다.

공식에서는 2가지 방식이 있는데 화면 바꾸는 것을 어디서 하는지에 따라 달라진다.

1. Via UI

캐시는 그대로 두고, 화면에 보여주는 값만 임시로 바꾼다. isPending(요청 진행 중 여부)과 variables(지금 보내려는 값)를 이용해서, 요청이 끝날 때까지만 화면에 낙관적인 값을 얹어 보여주는 방식이다. 캐시 자체는 건드리지 않으니 롤백 코드가 따로 필요 없고, 이 데이터를 보여주는 화면이 한 곳뿐일 때 적합하다.

function LikePost({ postId }: { postId: string }) {
  const { data: post } = useQuery({
    queryKey: ["post", postId],
    queryFn: () => fetchPost(postId),
  });

  const { mutate, isPending, variables } = useMutation({
    mutationFn: (liked: boolean) => likePost(postId, liked),
    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: ["post", postId] });
    },
  });

  // 요청 중이면 서버 데이터 대신 "지금 보내려는 값"으로 화면만 살짝 보여줌
  const displayedLiked = isPending ? variables : post?.liked;

  return (
    <button onClick={() => mutate(!post?.liked)}>
      {displayedLiked ? "❤️" : "🤍"}
    </button>
  );
}

2. Via the cache

onMutate에서 캐시(queryClient.setQueryData)를 직접 수정한다. 캐시가 바뀌면 같은 쿼리키를 구독하는 모든 컴포넌트가 동시에 갱신된다. 다만 실패했을 때는 캐시를 직접 되돌려야 하므로, onMutate에서 스냅샷을 저장해뒀다가 onError에서 복구하는 코드가 필요하다. 같은 데이터를 여러 화면에서 보여줄 때 적합하다.

function useLikePostMutation(postId: string) {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: (liked: boolean) => likePost(postId, liked),

    onMutate: async (liked) => {
      await queryClient.cancelQueries({ queryKey: ["post", postId] });
      const previous = queryClient.getQueryData(["post", postId]);

      queryClient.setQueryData(["post", postId], (old: any) => ({
        ...old,
        liked,
      }));

      return { previous };
    },

    onError: (_err, _liked, context) => {
      if (context?.previous) {
        queryClient.setQueryData(["post", postId], context.previous);
      }
    },

    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: ["post", postId] });
    },
  });
}

팀에서 어떻게 적용했나

미션 목록은 리스트 자체 말고도 다른 곳에서 같은 데이터를 참조하기 때문에, Via the cache 방식으로 적용했다.

Before

처음 구현에서는 캐시 대신 컴포넌트 로컬 useState로 화면에 보이는 배열을 따로 관리했다.

// 리팩토링 전 (요약)
const [items, setItems] = useState(missions);

const handleDragEnd = async (event) => {
  const reordered = arrayMove(items, oldIndex, newIndex);
  setItems(reordered); // 로컬 state만 먼저 바꿈
  try {
    await reorderAdminMissionsAsync({
      eventId,
      missionIds: reordered.map((m) => m.id),
    });
  } catch {
    setItems(items); // 실패 시 롤백
  }
};

After

캐시가 바뀌면 화면도 같이 바뀌니, 로컬 state와 로딩 플래그는 더 이상 필요 없어졌다. 수정·삭제 mutation도 그대로 적용한다.

// features/admin/missions/adminMissionMutations.ts
export function useReorderAdminMissionsMutation() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: ({ eventId, missionIds }: ReorderMissionsVariables) =>
      requestJson(
        `/api/v1/admin/events/${eventId}/missions/reorder`,
        createJsonRequest("PUT", { missionIds }),
      ),

    onMutate: async ({ eventId, missionIds }) => {
      // 진행 중인 refetch가 낙관적 업데이트를 덮어쓰지 않도록 취소
      await queryClient.cancelQueries(adminMissionQueryOptions.list(eventId));

      // 롤백용 스냅샷
      const previous = queryClient.getQueryData<AdminMissionDetail[]>(
        adminMissionQueryOptions.list(eventId).queryKey,
      );

      // 캐시를 직접 낙관적으로 갱신
      queryClient.setQueryData<AdminMissionDetail[]>(
        adminMissionQueryOptions.list(eventId).queryKey,
        (old) => {
          if (!old) return old;
          return missionIds
            .map((id, index) => {
              const mission = old.find((m) => m.id === id);
              return mission ? { ...mission, sortOrder: index + 1 } : null;
            })
            .filter(Boolean) as AdminMissionDetail[];
        },
      );
      return { previous };
    },

    onError: (_, { eventId }, context) => {
      if (context?.previous) {
        queryClient.setQueryData(
          adminMissionQueryOptions.list(eventId).queryKey,
          context.previous,
        );
      }
    },

    onSettled: (_, __, { eventId }) => {
      queryClient.invalidateQueries(adminMissionQueryOptions.list(eventId));
    },
  });
}

마치며

참 중요한 개념인데 모르고 있다는 것이 되게 부끄러웠다. 그리고 탄스택쿼리가 참 생각보다 많이 편리한 녀석이구나를 두번 세번 알면 알수록 깨닫는중이다. 초기에 나왔을때 사용해봤었는데 솔직히 그땐 딱히 장점이 없어서 사용이유를 잘 모르고 사용했다. 근데 지금은 뭔가 깊게 공부하다보니 참 흥미롭다. 이런 기능을 꼭 실무에서도 써볼수 있길...
