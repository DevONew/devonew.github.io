브로셔 안내 오버레이, 최적의 방법을 찾아서

📅2026년 6월 11일
StamploTeam ProjectFrontendTroubleshootingNext.jsSSR

개요

브로셔는 여러 장의 이미지를 슬라이드로 넘겨보는 페이지다. 팀원들과 협의 중, 유저가 제일 처음 들어오면 좌우로 넘길 수 있다는 것을 캐치하기 힘들거 같아 최초 진입 시에만 "터치해서 페이지 이동하기" 안내를 반투명 오버레이로 덮기로 했다. 이게 그렇게까지 많이 고칠줄은 몰랐는데 그래도 덕분에 여러 전략을 정리해보았다.

1. localStorage, 그리고 SSR 에러

가장 먼저 떠오르는 방법은 localStorage였다. 단순 state로만 처리하기엔 컴포넌트가 재마운트될 때마다 초기값으로 리셋돼서 컴포넌트 생명주기를 벗어나는 값을 기억할 수 없었다. 따라서 영속적으로 상태를 기억하는 무언가가 필요했고 그게 무난한 localStorage를 고른 이유였다.

// 가장 초기 페이지 — app/(user)/event/[eventId]/brochure/page.tsx
"use client";

import { useState } from "react";
import { use } from "react";
import BrochureSlider from "@/components/user/brochure/BrochureSlider";
import BrochureIndicator from "@/components/user/brochure/BrochureIndicator";
import BrochureGuideOverlay from "@/components/user/brochure/BrochureGuideOverlay";

const images = [
  "/images/image_brochure.png",
  "/images/image_brochure2.png",
  "/images/image_brouchure3.png",
];

type PageProps = {
  params: Promise<{ eventId: string }>;
};

const BrochurePage = ({ params }: PageProps) => {
  const { eventId } = use(params);
  const storageKey = `brochure_guide_seen_${eventId}`;

  const [currentIndex, setCurrentIndex] = useState(0);
  const [showGuide, setShowGuide] = useState(
    () => !localStorage.getItem(storageKey),
  );

  const handleDismiss = () => {
    localStorage.setItem(storageKey, "1");
    setShowGuide(false);
  };

  const handlePrev = () => {
    setCurrentIndex((prev) => (prev === 0 ? prev : prev - 1));
  };

  const handleNext = () => {
    setCurrentIndex((prev) => (prev === images.length - 1 ? prev : prev + 1));
  };

  return (
    <div className="bg-gomin-white flex flex-col items-center pt-4 pb-10">
      <div className="mb-4">
        <BrochureIndicator total={images.length} currentIndex={currentIndex} />
      </div>
      <BrochureSlider
        images={images}
        currentIndex={currentIndex}
        onPrev={handlePrev}
        onNext={handleNext}
      />
      {showGuide && <BrochureGuideOverlay onDismiss={handleDismiss} />}
    </div>
  );
};

export default BrochurePage;

로컬에서 테스트를 하자마자 에러가 났다. 브라우저 창 에러는 localStorage is not defined.

원인은 'use client'에 대한 오해에 있었다. 'use client'는 "이 컴포넌트가 브라우저에서 실행된다"는 뜻이 아니라 "이 컴포넌트가 브라우저에서도 상호작용 가능하다"는 뜻이었다. Next.js는 클라이언트 컴포넌트도 SSR을 거치는데, localStorage는 브라우저에만 있는 값이다 보니 useState 초기값 계산 함수가 그 서버 렌더링 시점에 바로 실행되면서 존재하지 않는 localStorage를 참조해 에러가 난 것이었다.

또 다른 의문

여기서 또 다른 의문이 들 수도 있는데 useState는 브라우저 전용 기능이 아닌가? 라고 생각할 수 있다.
왜냐면 서버에 있는 값은 바뀌지 않고 브라우저에서 상태를 관리 해주기 때문이다. 하지만 '브라우저 전용 기능' 과 '브라우저에서 상태를 관리해주는 것'은 엄연히 다른 말이다.

"브라우저 전용 기능"은 브라우저 API - localStorage, document, window -, 즉 브라우저가 제공하는 전역객체다.
"브라우저에서 상태를 관리해주는" useState 는 "React 컴포넌트가 렌더링될 때마다 특정 값을 기억하게 해주는" React 자체의 매커니즘이다.

useState는 자바스크립트 함수와 클로저로 구현된 로직이라, 이 코드를 실행할 수 있는 환경이라면 Node.js든 브라우저든 상관없이 똑같이 동작한다. 즉, useState 자체는 서버에서 멀쩡히 도는데, useState에 넘긴 초기값 계산 함수 안에서 브라우저 전용 API를 불렀다는 게 문제였다.

2. SSR을 해결하기 위한 window 객체 분기

그렇다면 위 문제는 결국 SSR 때 localStorage가 없는 게 문제였으니, 서버에서 실행될 때는 localStorage를 건드리지 않게 하면 되는 거 아닌가? 그래서 지금 코드가 서버에서 도는지 브라우저에서 도는지 구분할 수 있는 window 객체의 존재 여부로 분기 처리를 해주었다.

"use client";

import { useState, use } from "react";
import BrochureGuideOverlay from "@/components/user/brochure/BrochureGuideOverlay";

type PageProps = {
  params: Promise<{ eventId: string }>;
};

const BrochurePage = ({ params }: PageProps) => {
  const { eventId } = use(params);
  const storageKey = `brochure_guide_seen_${eventId}`;

  const [showGuide, setShowGuide] = useState(
    () =>
      typeof window === "undefined" || !localStorage.getItem(storageKey)
  );

  const handleDismiss = () => {
    localStorage.setItem(storageKey, "1");
    setShowGuide(false);
  };

  return (
    <div className="bg-gomin-white flex flex-col items-center pt-4 pb-10">
      {showGuide && <BrochureGuideOverlay onDismiss={handleDismiss} />}
    </div>
  );
};

export default BrochurePage;

하하, 이렇게 넣었더니 새로운 문제가 발생했는데 새로고침을 하면 hydration mismatch 에러가 생겼다.

이 문제의 원인은 서버는 typeof window === "undefined"가 항상 참이라 showGuide를 true로 렌더링하는데, 브라우저는 localStorage에 이미 저장된 값을 실제로 확인해 showGuide가 false가 될 수 있어서, 서버와 클라값이 서로 달랐기 때문이다. 문제를 해결하기 위해선 첫 렌더만큼은 서버와 클라이언트가 항상 같은 값을 내도록 만들고, 진짜 값은 마운트가 끝난 뒤에 반영되게 했다. 그래서 초기값은 항상 true로 고정하고, useEffect 안에서만 localStorage를 확인해 상태를 갱신하도록 코드를 추가했다.

const [showGuide, setShowGuide] = useState(true);

useEffect(() => {
  setShowGuide(!localStorage.getItem(storageKey));
}, [storageKey]);

코드적으로는 어떻게 해결된 거 같아보였으나 결국 바뀐값을 넣는거다 보니 화면에서는 오버레이가 생겼다가 사라지게 되는 현상이 보여 이 방법은 패스.

3. dynamic import로 SSR 꺼버리기

위에 상기한 문제로 이 컴포넌트를 아예 서버에서 렌더링하지 않도록 우회하는 방법을 썼다.
next/dynamic으로 { ssr: false } 옵션을 주면 이 컴포넌트는 서버에서 스킵되고 브라우저에서만 렌더링된다.

import dynamic from "next/dynamic";

const BrochureGuideOverlay = dynamic(
  () => import("@/components/user/brochure/BrochureGuideOverlay"),
  { ssr: false },
);

해치웠나

hydration mismatch같은 에러는 당연히 안나고 일단 구현 상으로는 완료 했으나... CSR이다 보니 오버레이가 한 박자씩 늦게 나타났는데 이게 참... 너무 거슬렸다. 사실상 useEffect 넣은 것과 결과물이 엇 비슷한 상황이 되었다. 아무래도 이 화면에서는 localstorage를 쓰는 전략이 옳지 않았던 거 같다. 아무튼 일단 기능 자체는 구현이 되었으니 2차 mvp 기간때 디테일을 잡아보기로 하고 다른 메인 피처들을 치러가게 된다.

4. 쿠키로 설정하기

우선 쿠키로 바꾸기 전에 로직이 좀 바뀌게 되었는데 브로셔 페이지가 서버 컴포넌트로 바뀌고 UX가 개선 되었다.
저 화면에서의 오버레이가 늦게 뜨는 것을 해결하고 시작 시 바로 오버레이가 보이기 위해선 서버단에서 애초에 처리하고 가는 게 낫다고 판단해 쿠키로 설정하게 수정했다.

쿠키 설정한 브로슈어 서버 페이지

// app/(user)/event/[eventId]/brochure/page.tsx
import { cookies } from "next/headers";
import { getEntryEvent } from "@/features/qr/entry/api/entry";
import BrochureClient from "@/components/user/brochure/BrochureClient";
import { redirect } from "next/navigation";

type Props = {
  params: Promise<{ eventId: string }>;
};

const BrochurePage = async ({ params }: Props) => {
  const { eventId } = await params;

  const event = await getEntryEvent(eventId);

  if (!event.brochureImageUrl?.length) {
    redirect(`/event/${eventId}/mission`);
  }

  const cookieStore = await cookies();
  const guideSeen = cookieStore.has(`brochure-guide-seen-${eventId}`);

  return (
    <BrochureClient images={event.brochureImageUrl} showGuide={!guideSeen} />
  );
};

export default BrochurePage;

오버레이 컴포넌트 페이지

// components/user/brochure/BrochureGuideOverlay.tsx
"use client";

import { useState, useEffect } from "react";
import OverlayCircleIcon from "@/components/icons/OverlayCircleIcon";

const BrochureGuideOverlay = ({ eventId }: { eventId: string }) => {
  const [visible, setVisible] = useState(
    () => !document.cookie.includes(`brochure-guide-seen-${eventId}`),
  );

  useEffect(() => {
    const prevent = (e: TouchEvent) => e.preventDefault();
    if (visible) {
      document.addEventListener("touchmove", prevent, { passive: false });
    }
    return () => {
      document.removeEventListener("touchmove", prevent);
    };
  }, [visible]);

  const handleDismiss = () => {
    document.cookie = `brochure-guide-seen-${eventId}=1; path=/; max-age=31536000`;
    setVisible(false);
  };

  if (!visible) return null;

  return (
    <div
      className="fixed inset-0 z-50 flex flex-col items-center justify-center bg-[rgba(17,17,17,0.5)]"
      onClick={handleDismiss}
    >
      <div className="-translate-y-15 flex flex-col items-center">
        <p className="text-gomin-white font-bold text-2xl text-center leading-snug">
          터치해서 페이지 이동하기
        </p>
        <div className="flex items-center gap-20 mt-2">
          <OverlayCircleIcon />
          <OverlayCircleIcon />
        </div>
      </div>
    </div>
  );
};

export default BrochureGuideOverlay;

이 시점엔 "쿠키를 봤는지"를 세 군데에서 겹쳐 확인하고 있었다. 서버 컴포넌트인 page.tsx가 cookies()로 쿠키 유무를 먼저 판단해 showGuide prop을 만들고, 중간의 BrochureClient는 그 값을 그대로 받아 오버레이를 렌더할지 말지 조건으로 쓴다. 렌더된 BrochureGuideOverlay는 또 자체적으로 document.cookie를 직접 읽어 자기 안의 visible state를 따로 계산했다.

겹쳐 보여도 실은 막으려는 케이스가 달랐다. 서버(page.tsx)의 쿠키 체크는 새로고침 대응, BrochureGuideOverlay의 쿠키 체크는 뒤로가기 대응이었다. 뒤로가기는 캐시에서 컴포넌트를 복원할 뿐 서버가 재실행되지 않아 서버 prop이 최초 값에 고정되는데, 그래서 자식은 마운트될 때마다 쿠키를 다시 읽게 설정 했다.

자식쪽에서 워낙 커버칠 수 있는 영역이 많아 부모쪽(page.tsx)의 쿠키 체크가 불필요하다고 생각했는데 기가 막히게 제거 하고 난 뒤 에러가 생겨 다시 넣어 해결했다.

마치며

결국 이 페이지에서 맞는 전략은 쿠키 사용이었다. 다른 전략들이 코드적으로 틀렸던 것은 아니다.
단지 이 요구 사항과는 다른 방향이었을 뿐, 분명 다른 상황에서는 유용하게 쓰일 전략들이다. 이미 알고 있던 개념들을 다시 깊게 파고들면서 지금 하는 작업과 연결 지어볼 수 있어 좋았다. 덕분에 개념 자체에 대한 이해도 한층 단단해졌고...
그리고 코드만 치고 넘어가는 데서 그치지 않고 내 방식대로 정리해보면서, 겪었던 문제와 그 과정이 머릿속에 훨씬 또렷하게 남는 시간이었다.
