초기 세팅을 맡게 된 이유

원래 초기 세팅은 내 몫이 아니었다. 하겠다는 팀원이 따로 있었다. 그런데 업무 분배를 하다 보니 그 팀원은 팀장이자, CI/CD 담당이자 백엔드 담당까지 너무 많은 업무를 맡고 있었다는 것이다.(돌발 상황)

누군가는 이 업무를 가져와야 하는 상황이었고, 나는 핏펫에서 처음 동물등록제 어드민 페이지를 구축할 때 초기 세팅을 담당해본 경험이 있어 이 역할을 맡기로 했다. 또한 새롭고 기존 실무에서 써보지 못했던 기술들로 초기 세팅을 해보고 싶은 마음도 있었다.

기술 스택 및 선택 이유

여기 있는 기술들은 팀원들과 함께 협의해서 정했고, 이후 개발을 진행하면서 필요한 스택을 계속 추가해왔다.
(2026.06.14 기술스택 일부 추가)

Next.js 16 (App Router)

사실 어드민과 유저 페이지만 놓고 보면 SSR이나 SEO가 크게 필요하지 않았다. 둘 다 로그인 이후 진입하는 화면이라 CSR로도 충분했고, 그래서 처음엔 Next.js가 꼭 필요한지 팀 내에서 논의가 있었다. 하지만 서비스 소개용 랜딩 페이지가 추가로 필요해지면서 검색 노출이 중요한 페이지가 생겼고, SEO를 위해 서버에서 렌더링할 방법이 필요해져 Next.js를 채택하기로 했다. 팀 전체가 최신 Next.js 16을 직접 다뤄보고 싶었던 것도 이유 중 하나였다.

pnpm

나중에 어드민과 유저 앱을 분리할 가능성을 염두에 두고, 확장하기 쉬운 pnpm을 처음부터 쓰기로 했다.(모노레포 고려) 패키지를 한 곳에 모아두고 필요한 것만 링크하는 방식이라 설치가 빠르고 용량도 적게 들며, 설치하지 않은 패키지는 코드에서 import할 수 없어 의존성 관리가 깔끔하다.

ESLint , Prettier, Husky

ESLint는 Next.js 공식 룰셋에 eslint-config-prettier를 얹어 포맷 규칙 충돌을 없앴다. 문제는 Prettier였다. 설정 파일은 있어도 실제 적용 여부는 팀원 각자의 에디터 설정에 달려 있어서, 저장 시 자동 포맷이 꺼진 사람은 그대로 커밋해버렸다. 그래서 Husky의 pre-commit 훅에 lint-staged를 연결해, 에디터 설정과 무관하게 커밋되는 파일에 Prettier가 강제로 실행되도록 만들었다.

Zod + React Hook Form

처음엔 기존에 직접 짜던 유효성 검사 로직을 Zod로 대체할 생각이었는데, 폼 상태 관리까지 맡길 수 있는 React Hook Form을 함께 도입했다. RHF는 비제어 컴포넌트 방식이라 입력할 때마다 불필요한 리렌더링이 없고, Zod 스키마 하나로 타입 추론과 런타임 검증을 동시에 처리할 수 있다는 점이 컸다.

TanStack Query v5

TanStack Query를 쓴 이유는 크게 세 가지였다.

가장 큰 이유는 서버 상태와 클라이언트 상태를 분리할 수 있다는 점이었다. queryOptions로 쿼리 정의를 한 곳에 모아두면 서버 컴포넌트의 prefetchQuery와 클라이언트의 useQuery가 이를 그대로 공유할 수 있어, 서버에서 미리 채운 데이터를 클라이언트가 하이드레이션하는 패턴을 별도 동기화 코드 없이 구현할 수 있었다. 그래서 서버 컴포넌트에서는 fetch를 쓰고, 클라이언트에서 실시간 갱신이 필요한 곳에만 TanStack Query를 섞어 쓰는 방식을 택했다. 이는 Next.js에서도 권장하는 패턴이었다.

두 번째는 낙관적 업데이트였다. 어드민 미션 수정 시 서버 응답을 기다리는 동안 화면이 disabled 처리되는 문제가 있었는데(이슈 #246), 팀원이 TanStack Query의 낙관적 업데이트로 해결했다(PR #252). onMutate에서 캐시를 먼저 갱신해 화면에 즉시 반영하고, 실패하면 onError에서 롤백하는 패턴을 표준으로 제공해줘서 직접 구현하지 않아도 됐다.

세 번째는 캐싱이었다. 대시보드처럼 여러 컴포넌트가 같은 데이터를 참조하는 화면에서 staleTime을 쿼리별로 선언해두면 불필요한 재요청 없이 캐시를 재사용할 수 있었다. 쿼리 팩토리 패턴으로 queryKey를 한 곳에서 관리하기로 한 것도 이때 자리 잡았다.

Zustand

컴포넌트 트리 구조와 무관하게 상태를 공유해야 하는 곳에 쓰기 위해 나중에 채택했다. 어드민에서는 행사 수정 폼의 편집 상태를 트리상 멀리 떨어진 사이드바 네비게이션이 알아야 페이지 이탈을 막을 수 있었고, 유저 페이지에서는 미션 스탬프 애니메이션 트리거 상태를 여러 컴포넌트가 공유해야 했다. Provider 없이 훅처럼 바로 쓸 수 있고, selector로 필요한 값만 구독해 불필요한 리렌더링도 막을 수 있다는 점이 이런 상태에 잘 맞았다.

Tailwind CSS v4 + shadcn/ui

Tailwind는 마침 팀원들이 막 배운 v4를 실전에 써보고 싶어 했던 것도 있었지만, 실질적으로는 설정 파일 없이 CSS에서 직접 디자인 토큰을 정의할 수 있는 방식이 이 프로젝트와 잘 맞았다. 행사마다 대표 색상(primary_color)이 다르게 지정되는 도메인 특성상, CSS 변수 기반으로 테마를 관리하기가 v3보다 수월했다.

shadcn/ui는 모달, 드롭다운처럼 디자인이 따로 정해지지 않은 공통 컴포넌트를 매번 새로 만드는 비용을 줄이기 위한 선택이었다. 다른 UI 라이브러리와 다르게 컴포넌트 코드 자체가 프로젝트에 복사되어 들어오는 구조라, 필요할 때 자유롭게 수정할 수 있다는 점도 맞았다.

Framer Motion

CSS만으로는 선언적으로 다루기 번거로운 애니메이션에 썼다. 유저 페이지의 퇴장 전환, 어드민 대시보드의 숫자 카운팅과 차트 전환 효과에 사용하였다.

Supabase

기존에 제공되던 API가 우리가 원하는 방향과 맞지 않아 백엔드를 새로 세워야 했다. DB, Storage, Auth를 한 번에 제공해 별도 서버 없이 필요한 걸 다 채울 수 있었고, RLS로 데이터 접근 제어까지 간단히 처리할 수 있었다.

폴더 구조 및 설계 의도

app/
  (landing)/     # 랜딩 — 서비스 소개
  (user)/        # 유저 모바일웹 — QR 스캔, 미션 수행
  (admin)/       # 어드민 PC웹 — 운영자 실시간 현황 관리
components/      # 공용 + 화면별 UI 컴포넌트
features/        # 도메인별 API 호출 + React Query 훅
stores/          # Zustand 전역 상태
hooks/           # 공용 커스텀 훅
utils/           # 공용 유틸
types/           # 타입 정의
constants/       # 상수

라우트 그룹 분리 — (admin) / (user) / (landing)

어드민(PC)과 유저(모바일)는 레이아웃, 인증 방식, UI가 완전히 달랐다. 하나의 저장소 안에서 사실상 다른 세 개의 화면을 관리해야 했기 때문에, 처음부터 라우트 그룹으로 갈라놓고 시작했다.

components vs features 분리

화면을 그리는 책임(component)과 API 호출·쿼리 로직 같은 비즈니스 로직(features)을 분리했다. 컴포넌트가 점점 비대해지는 걸 막고, 로직을 재사용하기 쉽게 하기 위한 구조다. FSD도 검토했지만 채택하지 않았다. 레이어와 slice 경계를 팀 전체가 공유하려면 그 자체로 학습 비용이 드는데, 1차 mvp 까지 개발 기간이 너무 짧았고 팀원 모두가 FSD 경험이 없는 상태에서 구조를 이해하는 데 시간을 쓰기보다는 바로 적용 가능한 단순한 구조가 낫다고 판단했다. 대신 features 안에서 관리자/참여자/QR처럼 도메인별로 폴더를 나누고, 도메인에 상관없이 똑같이 쓰이는 API 호출 코드는 shared로 따로 뺐다. 그 덕분에 FSD를 그대로 쓰지 않고도, 얻고 싶었던 이점인 관심사 분리와 코드 재사용은 충분히 챙길 수 있었다.

alias는 프로젝트 컨벤션에 맞춰 다시 정리

shadcn/ui는 기본적으로 lib/utils를 alias로 쓰지만, 우리 프로젝트는 이미 utils/로 통일하기로 한 상태였다. components.json의 alias 설정을 @/utils로 바꾸고, lib/utils.ts를 없앤 뒤 필요한 함수를 utils/index.ts로 옮겼다. 작은 설정 하나였지만, 초반에 이런 걸 안 맞추고 넘어가면 나중에 팀원마다 import 경로가 제각각이 되는 걸 여러 번 봐서 처음부터 손을 봤다.

타입 컨벤션 — interface와 type을 나눠 쓰기

솔직히 type과 interface중에 고르는건 취향 차이라고 생각했는데 찾아보니 설계 철학이 달랐다. type은 객체든 유니온이든 원시 타입이든 뭐든 이름을 붙일 수 있는 범용 별칭이고, interface는 객체지향의 인터페이스 개념을 따와 extends로 확장하고 선언 병합까지 되는, 객체의 계약을 기술하기 위한 문법이다. props는 유니온이나 Pick/Omit 조합이 섞이는 경우가 많아 type이 더 잘 맞았고, 응답 모델처럼 확장 가능성이 있는 객체 계약은 interface가 더 맞아서, props는 type으로 선언하고 그 외 타입은 interface를 쓰기로 정했다.

proxy.ts로 접근 제어의 뼈대만 먼저

Next.js 16부터는 middleware.ts 대신 proxy.ts를 쓴다. 역할은 같다 — 페이지에 들어가기 전에 인증을 확인하는 것. 어드민 경로와 유저 경로 각각에 어떤 검증이 필요한지 뼈대만 잡아두고, 실제 로직은 이후 기능 개발 단계에서 채워 넣도록 넘겼다.

마치며

React Hook Form을 제안할 때 나는 Zod와의 궁합을 근거로 들었는데 팀원은 납득이 되지 않았고, 나중에 팀원이 짚어준 "리렌더링이 없다"는 성능 이유로 도입이 결정된 적이 있었다. 돌이켜보면 근거 자체가 틀렸다기보다, 그 근거를 확신을 갖고 설명하지 못했던 탓이 컸다. 확신은 아는 만큼에서 나오는데, 어중간하게 알고 있으니 설명도 어중간했던 것이다. 같은 기술도 얼마나 깊이 알고 있느냐에 따라 설득력이 달라진다는 걸 그때 느꼈다. 이번 초기 세팅에서 기술 스택 하나하나의 근거를 정리하고 출처까지 남겨보려 한 것도 이 경험 때문이다. 다음에 누군가를 설득해야 할 때는, 아는 것에서 그치지 않고 확신을 갖고 설명할 수 있을 만큼 알아둘려고 한다. (그리고 이것은 추후 블로그에 적을 AI 사용과도 연관이 있다..!!)
