## 개요

우리 팀은 업무 티켓과 이슈를 별도 툴 없이 GitHub로 관리했다. 일이
생기면 우선 이슈 티켓을 만들어두는 식이었는데, 어떤 이슈를 고치고 pr을 날릴때 관련된 이슈를 찾고 pr을 쓰는게 생각보다 병목이 생겼다.
또한 pr 팀 컨벤션이 있음에도 하나씩 자꾸 빠트리는 휴먼 에러도( 태그를 걸지 않거나 프로젝트를 설정해두지 않거나 본문에 표기할 내용들을 빼먹는 등) 꽤나 있는 편..
그래서 이 프로세스를 어떻게 하면 줄일 수 있을지 고민하다 github CLI와 클로드의 skill을 합쳐 업무 관리 쪽을 자동화 해보기로 했다!

## Github CLI

github.com, aws.com, Docker… 이런 서비스들, 대부분 CLI(Command Line Interface) 를 공식으로 제공하고 있다.
`gh`는 Github 공식 CLI다. 브라우저 없이 터미널에서 PR 생성, 이슈 조회, 레포 클론을 명령어 한 줄로 처리할 수 있다.

#### 내가 주로 쓴 gh 명령어들

```bash
gh auth login
gh pr list
gh pr create
```

MCP로 연결하는 방법도 있지만, CLI가 있다면 AI가 직접 명령어를 실행하는 게 훨씬 빠르고 정확하다.

## 어떻게 사용했나

### /commands/pr 만들기

팀에 있는 pr 작성 컨벤션과 gh 명령어를 섞어 md를 만들었다.

아래는 내가 만든 `pr.md`의 전문이다.

````md
# PR 생성

현재 브랜치의 변경사항을 바탕으로 PR을 생성합니다.

## 절차

1. `git status` 로 커밋 안 된 변경사항을 확인합니다. 있으면 커밋을 먼저 진행합니다.
2. develop을 최신 상태로 업데이트하고 현재 브랜치에 rebase합니다.

   ```bash
   git checkout develop
   git pull origin develop
   git checkout -        # 직전 브랜치(현재 작업 브랜치)로 복귀
   git rebase develop
   ```

3. `pnpm build` 를 실행하여 빌드 성공을 확인합니다.
4. `git push -u origin HEAD` 로 브랜치를 push합니다.
5. `git log origin/main..HEAD --oneline` 과 `git diff origin/main...HEAD --stat` 로 변경 내용을 파악합니다.
6. `gh issue list` 로 이슈 목록을 확인하고 작업과 연관된 이슈를 찾습니다.
7. PR 제목과 본문 초안을 작성하여 사용자에게 보여주고 수정 요청을 받습니다. 연관 이슈는 본문에 `Related to #번호` 형식으로 추가합니다. (`Closes #번호` 는 머지 승인 후 사용합니다.)
8. 확인되면 아래 형식으로 PR을 생성합니다.

## 주의사항

- PR 본문에 `Co-Authored-By` 등 자동 서명을 추가하지 않습니다.

## PR 본문 형식

```

(변경 내용 1~2줄 요약, 불렛 포인트로 요점을 간결하게 적어주세요.)

## 왜 이렇게 했나요?

(선택한 이유, 다른 방법 대신 이걸 선택한 이유)

## 리뷰어가 특히 봐줬으면 하는 부분

( 변경,추가,생성된 부분에 에러가 없는지 의도된 동작대로 되는지 확인해주세요.)

## 스크린샷 (UI 변경 시)

없음

```

## 생성 명령어

```bash
# 브랜치 push (아직 안 된 경우)
git push -u origin HEAD

# PR 생성
gh pr create \
  --title "<제목>" \
  --body "<본문>" \
  --assignee DevONew \
  --reviewer sy3ra,hyeonseong2023,skylarkim22 \
  --label "review needed,D-2"
```

## 고정값

| 항목     | 값                                 |
| -------- | ---------------------------------- |
| Assignee | DevONew                            |
| Reviewer | sy3ra, hyeonseong2023, skylarkim22 |
| Label    | review needed, D-2                 |

```

```
````

절차가 8단계나 되지만 하나하나는 단순하다.  
커밋 여부 확인 → develop 최신화 → 빌드 확인 → push → 변경 범위 파악 → 연관 이슈 탐색 → 본문 초안 확인 → 생성, 순서로 실제로 pr전 무조건 해야되는 것이다.
이 순서를 매번 사람이 기억해서 챙기는 대신, 문서에 고정해 AI가 항상 같은 순서로 실행하게 만들었다.

Assignee, Reviewer, Label처럼 매번 같은 값을 입력해야 하는 항목은 아예 고정값으로 못박아서 "리뷰어 태그를 빠뜨렸다" 같은 실수를 없앴다.
(태그 쪽은 가끔씩 원하는 것에 따라 다르게 달기도 했는데 주로 저 태그면 pr의 90퍼센트는 커버된다.)
PR 본문 포맷(무엇을/왜/리뷰 포인트/스크린샷 4단 구성)도 팀에서 쓰던 템플릿을 넣었다.

### 제한 걸기

만든 것만큼 제약을 거는 것도 중요하다. 팀 단위로 가거나 스케일이
커지면 이 제약도 더 많아지겠지만, 우선은 나 혼자 쓰는 거라 간단하지만
확실한 제약만 걸어뒀다.

AI 혼자 끝까지 못 가게 승인 지점을 끼워 넣었다. PR 제목과 본문 초안은
항상 먼저 보여주고, 수정 요청을 받은 뒤에야 실제 생성 명령(`gh pr
create`)을 실행하게 했다. 절차 앞부분(커밋 확인, rebase, 변경 범위
파악, 이슈 탐색)은 AI가 알아서 진행하지만, 실제로 PR이 만들어지는
되돌리기 번거로운 지점 직전에는 반드시 사람 확인을 거치게 했다.

빌드 확인도 절차 중간에 강제로 넣었다. `pnpm build`가 성공해야만
push로 넘어가도록 순서를 고정했다. 하지 말아야 할 걸 막는 제한이라기
보다, 깨진 빌드로 PR이 올라가는 상황 자체를 절차 안에서 걸러내는
안전장치에 가깝다.

## 마치며

이 프로세스를 만들고 나서 시간이 많이 단축됐다. 개발한 걸 그대로
설명하면 되는 거 아니냐고 생각할 수 있지만, 막상 말로 풀어 쓰는 게
꽤 걸린다. 우리 팀은 코드리뷰가 워낙 꼼꼼해서 예상 질문에 대한 답까지
PR에 미리 적어둬야 했는데, 그것도 시간을 잡아먹는 이유 중 하나였다.
`/pr`을 만든 뒤로는 어떤 부분을 강조해야 할지, 예상 질문에 대한 답을
어떻게 녹여야 할지만 알려주면 알아서 정리해주니 훨씬 빨라졌다. `gh`
덕분에 이슈·PR 목록도 빠르게 찾을 수 있었고, 나중엔 원래 있던
`/review`도 같은 방식으로 다듬어 잘 썼다.

아쉬운 점도 있다. 스크린샷을 첨부할 수 없어서, 정말 중요한 것만
빼고는 PR에 사진을 거의 못 넣었다.

실무 레벨로 가면 훨씬 복잡해지고 본격적인 오케스트레이션이 필요할
것 같다. 처음부터 복잡하게 만들면 사고 날 확률만 높아지니, 이번엔
익숙해지는 셈 치고 기본부터 간단하게 만들어본 것에 가깝다.
