애니메이션을 맡게 된 이유

우선 1차 mvp가 필수 기능 개발 및 구현이었다면 2차 mvp는 이제 리팩토링과 2순위 기능 추가 개발 그리고 UI·UX 고도화였다. 애니메이션도 그 고도화 항목 중 하나였고, 1차 mvp 이후 받은 피드백에도 애니메이션 요청이 있었다. 우리는 어드민 페이지와 유저 페이지 양쪽 다 애니메이션을 넣기로 했었는데, 나는 유저사이드 쪽을 맡기로 팀원과 협의했다. 평소 여러 앱을 쓰면서 인터랙션을 직접 구현해보고 싶었지만 실무에서는 애니메이션을 다뤄볼 기회가 적었기 때문에 이번이 좋은 기회였다.

구현 해야 할 것들

유저 사이드에는 총 4 챕터가 있는데 입장하기, 브로셔페이지, 미션페이지, 리워드(미션완료 페이지)가 있다.
다른 페이지들은 특별한 이슈가 없었고 다 무난하게 구현했기 때문에 간략하게 정리, 생략하고 공을 많이 들인 미션 페이지를 상세히 써볼려고 한다.

입장하기와 브로셔 페이지

여기서는 상대적으로 애니메이션이 간단하게 들어가있다. 우선 사용자 경험을 고려 했을때 입장하기는 사실 상 별 정보가 없기에 빨리 다음 페이지로 넘어갈 것을 고려해 애니메이션 fade-out을 제거했다.

질문1: motion으로도 충분히 만들 수 있는 애니메이션인데 왜 그냥 CSS로 구현했는가.
음...정말 굳이라서 생각해서 쓰지 않았다. 진입 애니메이션은 한번 재생되고 끝나기 때문에 언제 끝났는지 코드가 알 필요가 없다. 또한 css로 구현할 수 있는것이기 때문에 앞으로 나오는 애니메이션 코드들은 웬만해선 css로 구현 했다.

반대로 브로셔 페이지는 슬라이드 페이지에서 바로 미션 페이지로 넘어가는 것이 흐름이 뚝 끊기고 어색하여 exit 애니메이션이 필요하다고 판단해 motion을 사용했다.

질문2: prefetch를 쓴 이유는?
exit 애니메이션이 끝난 뒤에야 라우팅이 시작돼서, 그 300ms만큼 다음 페이지 로딩도 늦게 시작됐다. 그래서 버튼을 누르는 시점이 아니라 마지막 장에 도달한 시점에 미리 다음 페이지를 받아두기로 했다. exit 애니메이션이 재생되는 동안 로딩이 백그라운드에서 함께 끝나, 라우팅되는 순간 화면이 바로 뜬다.

질문3: <Link>는 왜 안썼는가?
링크 컴포넌트를 안 쓴 이유는 "클릭 즉시 이동"이 아니라 "애니메이션 끝나고 이동"이 필요해서, 라우트 타이밍 때문에, 이동 시점을 코드가 직접 제어할 수 있는 router.push를 썼다. 참고로 <Link> 컴포넌트 안에 이 prefetch가 내장되어있다고 한다.

미션 페이지

미션 페이지는 지난번 브로셔 페이지 포스팅 마냥 여러 전략을 고려했다. 우선 애니메이션을 그냥 넣었을 때는 qr을 찍고 미션 페이지로 돌아올때마다 모든 스탬프의 애니메이션이 동작했다... 당연히 원하지 않는 동작이고 제일 최근에 클리어한 미션 스탬프만 애니메이션이 되어야 한다.

원하는 바를 위해선 가장 최근에 완료된 미션이 무엇인지부터 알아야 했는데, 미션 목록 API는 항상 최신 완료 상태를 통째로 내려줄 뿐 그중 무엇이 방금 새로 찍힌 건지는 알려주지 않는다. 새로 찍힌 미션 하나만 정확히 특정하는 것이 시작이라고 생각했다.

해결 방법 1. useRef 사용하기

가장 먼저 떠올린 방법은 useRef를 이용하는 것이었다. 기존 상태, 이전 완료 미션 목록을 저장해두고, 새 랜더와 비교해서 새로 늘어난 ID를 찾아 클라이언트 상태만으로 해결 할려고 했다.

하지만 QR을 찍고 미션 페이지로 돌아오는 방식이 router.push()가 아니라 window.location.assign()였다.
이게 왜 문제냐면 페이지가 새로 로드되기 때문에 React 컴포넌트 트리 자체가 통째로 사라지므로 useRef의 값도 이전 상태와 함께 초기화된다. 따라서 탈락..ㅜㅜㅜㅜ

window.location.assign()을 썼던 이유: router.push()를 쓰면 모바일에서 카메라 스트림이 붙어있게 되는 문제가 있어 의도적으로 하드 네비게이션을 쓰고 있다고 한다.

해결 방법 2. — sessionStorage 시용하기

페이지가 완전 새로 마운트라는 가정 뒤에서도 살아남을 수 있는 sessionStorage도 검토했다. 기술적으로는 가능했지만, 이 하나의 값을 동기시키고 별도 저장소를 새로 들여오는 게 과하다고 판단해 이것도 패스~

해결 방법 3. — URL 쿼리스트링 (?newMission=id) 넣기

해결 방법 4. — 스토어를 이용하기

이후, qr 카메라 페이지 쪽에서 window.location.assign()로 인해 뒤로가기 로직이 먹히지 않는 버그가 발생했고 그래서 qr 촬영 페이지를 qr 모달로 바꾸게 되었다. 이로 인해 애니메이션을 구현하는 방법에도 영향이 가게 되어 일부분을 수정하게 되었다.

위에서 말했듯 qr을 찍는 방법이 폰 내 네이티브 카메라로 찍는 방법과 웹 내 우리가 구현한 카메라로 찍는 게 있는데 후자 케이스를 콜백 + 전역 스토어로 바꾸게 되었다.

빵빠레 붙이기

마지막으로 모든 미션을 완료하면 빵빠레가 터지는 모션을 넣고 싶었다.
canvas-confetti 라이브러리를 사용했는데 별도 렌더링 없이 canvas에 직접 그려서 React 리렌더와 무관하게 동작하고, 번들 크기가 가볍고 커스터마이징이 자유롭다는 장점이 있다. MissionPageClient에 직접 넣었더니 코드가 너무 방대해져서 useCelebration 훅으로 분리했다.

// hooks/useCelebration.ts
export function useCelebration() {
  const hasCelebrationFired = useHasCelebrationFired();
  const markCelebrationFired = useMarkCelebrationFired();

  const handleStampReady = () => {
    if (hasCelebrationFired) return;
    markCelebrationFired();

    setTimeout(() => setShowCelebration(true), 600); // 축하 메시지 shake

    setTimeout(() => {
      import("canvas-confetti").then(({ default: confetti }) => {
        confetti({
          particleCount: 60,
          angle: 60,
          spread: 55,
          origin: { x: 0, y: 0.7 },
        });
        confetti({
          particleCount: 60,
          angle: 120,
          spread: 55,
          origin: { x: 1, y: 0.7 },
        });
      });
    }, 800);
  };

  return { showCelebration, handleStampReady };
}

마지막 미션 완료 여부를 확인하고 각 타이밍을 개별로 조절하기엔 복잡해서, 도장 애니메이션 → shake → 빵파레까지를 setTimeout 하나의 흐름으로 묶어 처리했다.

canvas-confetti는 모든 미션을 완료했을 때만 필요한 드문 케이스라 import("canvas-confetti")로 동적 import했다. gzip 기준 7KB 정도라 로딩 지연은 체감되지 않았다.

빵파레도 스토어로 관리하기

기존에는 onStampReady가 MissionStamp에만 연결되어 있어 리스트 뷰에서 빵빠레가 발생하지 않은 걸 발견했다. MissionItem에도 동일하게 onStampReady를 추가하고, 중복 방지 로직을 useRef 대신 zustand 스토어(hasCelebrationFired)로 교체해 뷰 전환 시 재실행을 막았다.

// stores/user.ts
export const userStore = create(
  combine(
    {
      newlyStampedMissionId: null as number | null,
      hasCelebrationFired: false,
    },
    (set) => ({
      clearNewlyStampedMissionId: () =>
        set({ newlyStampedMissionId: null, hasCelebrationFired: false }),
      markCelebrationFired: () => set({ hasCelebrationFired: true }),
    }),
  ),
);

마치며

길고 긴 애니메이션 작업이 끝났다. 사실 이 밖에도 구현한 애니메이션이 더 있지만, 상대적으로 기초적인 부분이라 여기서는 중요하게 생각한 것들만 세부적으로 정리했다. (나머지는 기초적인 부분이니까 ez) 애니메이션을 이만큼 붙여보면서 가장 크게 느낀 건 타이밍 이슈였다. 타이밍을 맞추는 게 생각보다 훨씬 까다로웠고, 이 문제 때문에 끝내 구현하지 못한 부분도 있다. SSR 특성상 useEffect가 가장 늦게 실행되다 보니, 그 안에서 타이밍을 맞추는 게 유독 어려웠다. 그래도 미션 스탬프가 찍히는 부분에서는 꽤 좋은 반응을 들어서 나름 뿌듯했다. 성능을 고려해 타협한 지점들이 있어 아쉬움도 남지만, 원했던 타격감은 잘 살아난 것 같아 만족스럽다.
